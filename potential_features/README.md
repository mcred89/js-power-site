work. These notes are proposals, not a committed roadmap or authorization to
implement them. Revisit the user's latest decision before starting a feature.

## Adding an idea

Create one Markdown file with a short descriptive filename and add it to the
table above. Start with the problem and concrete examples; keep tentative
recommendations separate from decisions the user has made. Update the existing
note when an idea evolves instead of creating competing plans.

Use these sections as a starting point; omit any that do not help:

- **Status and last discussed:** proposed, deferred, approved, or implemented;
  include the date and the user's latest decision.
- **Problem and examples:** what the user needs and why the current app falls short.
- **Proposed experience:** how someone would use it, with alternatives and tradeoffs.
- **Open decisions:** questions to resolve before implementation.
- **Implementation considerations:** affected code, persistence, compatibility,
  and boundaries to preserve. Recheck these against the current app when resuming.
- **Validation scenarios:** the important user flows and data-integrity cases.
- **Related work:** links to existing features, research, or other proposals.

When a feature ships, update its status and link to its implementation or user
documentation so future readers can distinguish the proposal from current behavior.
